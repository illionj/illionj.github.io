dll里面的导出函数
getprocess 是如何得知是stdcall  还是cde
如果不用.def文件  是不是 stdcall 不能得到原函数一样的名字  即使加了extern c也不行

如果用stdcall了 函数就一定会被改名  此时唯一的办法就是使用.def文件
使用stdcall之后 显示调用的过程中  也必须写明是stdcall

那么在linux中  stdcall是如何存在的  如果 导出函数也使用的stdcall
linux的dlopen能获取的真实名称
而且 linux是没有.def  它能否在函数导出的时候保持原本名称

linux中 extern "c"可以正常使用 不会被stdcall改名

对于64位设备  这些call都是没有意义的了 


so和dll的导出优缺点

dll的优点 有def文件可以控制c++乱改函数名称
有lib  可以直接隐式调用没有任何附加工作,并且可以导出类
支持函数重载

缺点 不能(非常繁琐)显式的导出类 
隐式调用(使用lib符号集)不能指定dll路径  只能是系统路径和进程exe所在路径
延迟调用可以缓解上面的问题,但是崩了不太好排查  和存在载入顺序问题

so的优点 全部函数直接就自动导出了  
可以指定so文件路径  so文件不限制位置  等同于win上dll的隐式调用  在此情况下可以随意使用类或任何函数 支持函数重载

缺点  如果想要显式调用,所有的函数必须增加extern c才能使用  无法阻止c++编译器乱改名
makefile里必须指定位置

所有linux比windows香太多了

c++函数改名不是瞎改的  它有统一的函数修饰手段规范 但g++和mvsc规则不一样

同一平台上对于同一个函数  修饰出来的函数一定是一样的,所以就等同于显式调用了


x64 的修饰出来的函数没有下划线了
似乎并不是这样的  同平台还是会有下划线

windows 伴生的lib里面 确实有符号  但这个符号是负责联系dll  并且告知编译器在使用过程中需要去链接
实际的情况还是 和linux一样  调用者对于函数产生了一样了 符号 编译器根据符号去寻找dll里面的同名函数

以下内容为x86_32
如果你返回一个结构体 编译器会在参数列表里面额外增加一个指针  然后在汇编层面就是直接操作此指针
因为返回结构体根本没有所谓的代价
不对还是有代价  不知道为什么汇编在申请类的时候总会多申请8个字节(内存对齐)
caller先在自己的栈帧里面申请将要返回的结构体的内存(但是比较奇怪  它会多8个字节)(callee的多4个字节)
并且入参会默认增加加一个指针  指向caller申请的栈内存
如果没有拷贝 汇编会调用 call    j__memcpy 用默认传入指针进行拷贝

如果有拷贝  汇编会把这个默认传入的指针作为this指针  它指向caller申请的那部分内存 进行拷贝操作

那这么说 以自定类型作为返回值  确实会有额外消耗 会多占用一次内存  并且存在多进行一次拷贝


1.     错误来源主要是重复定义的问题，并且重复定义的基本上都是VC Runtime和Standard C++ Library中的函数
2.     LIBCMT和LIBCPMT为Release下的Lib，原本不该该出如今Debug版本的连接的Lib中
3.     重复定义的问题主要出如今：LIBCMT, LIBCPMT, MSVCPRTD, MSVCRTD
来看看出问题的LIB是那些：
1.     LIBCMT：C Runtime库的多线程静态连接的Release版本
2.     LIBCPMT：C++ Standard Library的多线程静态连接的Release版本
3.     MSVCPRTD：C++ Standard Library的多线程DLL的Debug版本
4.     MSVCRTD：C Runtime Library的多线程DLL的Debug版本
当前咱们的配置是多线程DLL的Debug版，所以3和4是应该出如今link的列表中的，不属于多余。然后二者则是只是当多线程静态连接Release版中才会出现。这提示我在项目中加入的ANTLR.LIB多是形成这个问题的根源，由于静态库的编译选项很容易和主程序发生冲突，而且根据实际信息咱们能够看出ANTLR.LIB应该是用多线程静态连接的Release版原本编译的。
解决方法：
   一、首先查看编译项目依赖的其余项目的运行时库是否一致
   二、若是不一致，改成一样的运行时库，如在下编译的是：“多线程调试 DLL (/MDd)”,如今须要把全部的依赖项目的运行时库都改成一致的库，就ＯＫ了。

简述  如果ff1里面没有定义了一个临时变量  那么msvc就会直接操作传进来的指针

简单概括一下  如果返回对象的函数里面存在临时变量  msvc 先完整生成临时变量
然后 在把这个临时变量移动(如果没移动就拷贝,没拷贝就默认复制)给入参指针的栈帧对象

然后 在caller 那里 mvsc又会调用一次析构函数去释放 入参指针的栈帧对象 

所以能看到两次析构一次构造 一次(移动/拷贝)  如果移动(拷贝)函数写的不好 类内存在指针变量  很容易产生重复释放问题

但是 在gcc/clang里面  如果函数返回一个对象  那么即使是-g模式  编译器也会忽视临时变量的产生
直接使用传入的栈帧指针进行操作


ps //如果没有显示定义拷贝  但显式定义了移动  拷贝会因为移动的存在被删除   三家编译器都是如此
移动构造函数 的noexcept是针对 stl容器  如果是直接手动 p=std::move(f); 
即使没有定义 noexcept 也会调用  但如果是  move vector  那么noexcept就不能少
但是如果你的这个类会被用在stl容器里面比如vector等  那么这个类的移动构造就必须标注noexcept
因为stl是甩锅小能手,拷贝没有风险 stl大大方方的操作.移动有风险,那么除非你给stl一个免责声明noexcept:
随便移,出问题算我的和你stl没关系.那么stl是是不会去调用你得移动函数,而依然走拷贝
这些都是针对stl容器的规定

没有可用的复制构造函数或复制构造函数声明为“explicit”  拷贝构造需要入参 增加const

函数指针遐思

虽然函数名称隐式衰减为指向函数的指针，但对于成员函数而言并非如此：要获得指向成员函数的指针，必须使用 &amp;., 
**(2)** std::bind() 检测到一个指向成员函数的指针被传递并且很可能将它变成一个可调用对象，
并且 **(3)** 使用指向成员函数的指针是一个对象需要。
当 std::bind() 使用指向成员的指针时， std::bind() 的第二个参数相应地需要指定对象来自何时。非常感谢！ (2认同)
