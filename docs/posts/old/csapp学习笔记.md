27.浮点数舍入
2.IEEE规定了4种舍入方案。

向偶数舍入、向零舍入、向上舍入、向下舍入。

系统默认采用   向最接近的值舍入（round-to-nearest）。这是基础，其他三种方式用于计算上下界。

即向最接近的设舍入（round-to-nearest）是一个总称。它具体采用哪一种方式要由具体情况而定。

1）当舍入方式发生分歧时，优先采用向偶数舍入。

无论是10进制数，还是二进制数，只有在数值为中间值时，才会发生纠纷。

例如：1.235，向上是 1.24；向下/向零 1.23。误差相同都是0.005。这时我们优先采用向偶数舍入，即1.24。

          1.245，向上是 1.25；向下/向零 1.24。误差相同都是0.005。这时我们优先采用向偶数舍入，即1.24。

而1.234999，我们保留两位小数时，就没有必要纠结。向上/向偶 1.24   误差为0.0050001；向下/向零 1.23  误差为0.0049999.向下的误差最小，所以系统会采用1.23。

在比如  1.2350001，舍入到1.24的误差值要小于舍入到1.23的误差值，没必要纠结。

35.大小端问题会在总线的位置被处理   
大小端模式处理器外部总线的位序也遵循着同样的规律，根据所采用的数据总线是32位，16位和8位，大小端处理器外部总线的位序有所不同。
大端模式下32位数据总线的msb是第0位，MSB是数据总线的第0~ 7的字段；而lsb是第31位，LSB是第24~ 31字段。
小端模式下32位总线的msb是第31位，MSB是数据总线的第31~ 24位，lsb是第0位，LSB是7~ 0字段。
大端模式下16位数据总线的msb是第0位，MSB是数据总线的第0~ 7的字段；而lsb是第15位，LSB是第8~ 15字段。
小端模式下16位总线的msb是第15位，MSB是数据总线的第15~ 7位，lsb是第0位，LSB是7~ 0字段。
大端模式下8位数据总线的msb是第0位，MSB是数据总线的第0~ 7的字段；而lsb是第7位，LSB是第0~ 7字段。
小端模式下8位总线的msb是第7位，MSB是数据总线的第7~ 0位，lsb是第0位，LSB是7~0字段。

57.内存分配函数
函数原型：void* calloc（unsigned int num，unsigned int size）；
功能：在内存的动态存储区中分配num个长度为size的连续空间，函数返回一个指向分配起始地址的指针；如果分配不成功，返回NULL。

从本质上来说，malloc（Linux上具体实现可以参考man malloc，glibc通过brk()&mmap()实现）是libc里面实现的一个函数，如果在source code中没有直接或者间接include过stdlib.h，那么gcc就会报出error：‘malloc’ was not declared in this scope。如果生成了目标文件（假定动态链接malloc），如果运行平台上没有libc（Linux平台，手动指定LD_LIBRARY_PATH到一个空目录即可），或者libc中没有malloc函数，那么会在运行时（Run-time）出错。new则不然，是c++的关键字，它本身不是函数。new不依赖于头文件，c++编译器就可以把new编译成目标代码（g++4.6.3会向目标中插入_Znwm这个函数，另外，编译器还会根据参数的类型，插入相应的构造函数）。
在使用上，malloc 和 new 至少有两个不同: new 返回指定类型的指针，并且可以自动计算所需要大小。而 malloc 则必须要由我们计算字节数，并且在返回后强行转换为实际类型的指针。另外有一点不能直接看出的区别是，malloc 只管分配内存，并不能对所得的内存进行初始化，所以得到的一片新内存中，其值将是随机的。除了分配及最后释放的方法不一样以外，通过malloc或new得到指针，在其它操作上保持一致。 [2]

2.干扰编译器优化的情况
因为编译器的最重要的原则是完整无误的编译源码,所以对于任何二义性操作,它都会保持最保守的优化态度,简称不优化
a.内存别名使用
当传入两个指针(或者引用)编译器需要考虑两个指针指向同一个内存(或者同一处内存的不同位置),即这两个指针所指向的内容互相影响.
这种情况就需要开发人员手动优化
b.存在函数调用的情况
因为编译器无法预知函数调用是否存在副作用,比如修改全局变量等等,所以编译器不会优化函数调用的顺序


3.具体优化示例
a.消除循环的低效率
把一些不会变的函数结果从循环中移至初始化中 比如strlen()
因为编译器不知道strlen会不会改变,所以它必须假设它会变,因此编译器无法优化循环中不变的strlen参考上面2
此操作叫做代码移动

b.减少过程调用
比如获取头指针等等  类似a

c.消除不必要的内存引用
编译器面对指针时会十分小心
当入参是一个指针,这个指针又再循环中被反复修改,编译器往往会使用最保守的策略:
每次循环前先读指针 操作 再写入  如果设置临时量的话只需要初始化读一次  结束再赋值即可
编译器不能优化的原因是 假设这个指针和操作里面的东西有关联,那么每次读写 都会影响其内部的值

7.13 dlopen

可执行文件 -rdynamic

选项 -rdynamic 用来通知链接器将所有符号添加到动态符号表中
（目的是能够通过使用 dlopen 来实现向后跟踪）
-rdynamic
Pass the flag ‘-export-dynamic’ to the ELF linker, on targets that support
it. This instructs the linker to add all symbols, not only used ones, to the
dynamic symbol table. This option is needed for some uses of dlopen or to
allow obtaining backtraces from within a program.


在 Linux 中，-rdynamic 选项是一个链接器标志，它指示链接器将所有符号（包括那些未被程序引用的符号）添加到正在创建的可执行文件或共享库的动态符号表中。

这个选项通常在创建共享库时使用，因为它允许在运行时解析库中的符号，即使它们没有被程序直接引用。 这在程序需要动态加载插件或模块的情况下非常有用，并且需要能够解析这些模块中的符号而不直接链接到它们。

-rdynamic 选项也可以在链接可执行文件时使用，但通常"没有必要"，除非程序使用动态加载或其他高级动态链接技术。

值得注意的是 -rdynamic 选项会增加可执行文件或共享库的大小，因为它包括所有符号，无论它们是否实际使用。 此外，如果程序设计不当，也会带来安全风险，因为它可能允许攻击者利用动态符号表中的漏洞执行任意代码。

在 Linux 中，-export-dynamic 链接器选项类似于 -rdynamic 选项，因为它还指示链接器将所有符号添加到正在创建的可执行文件或共享库的动态符号表中。 但是，它在处理符号可见性的方式上有所不同。

使用 -export-dynamic 选项时，链接器将仅导出在源代码或链接描述文件中明确标记为导出的符号。 这意味着默认情况下并非所有符号都会导出，开发人员必须明确指定应导出哪些符号。

在创建需要在运行时向其他程序公开特定符号的共享库时，此选项很有用。 通过仅导出必要的符号，生成的共享库将更小并且不太可能向外部程序公开不必要的功能。

值得注意的是，-export-dynamic 选项通常在构建共享库时使用，在构建可执行文件时不太常用。 此外，与 -rdynamic 选项一样，如果程序设计不当，使用 -export-dynamic 可能会带来安全风险，因为它可能允许攻击者利用动态符号表中的漏洞执行任意代码。


如果共享库的静态符号表中存在与可执行文件同名的符号，则链接器可能会产生错误或警告，具体取决于所使用的链接选项。

将程序与共享库链接时，链接器会搜索程序中定义的符号以及程序使用的任何共享库。 如果在多个地方发现同名符号，链接器必须决定使用哪个符号。

默认情况下，链接器将优先使用程序中定义的符号而不是共享库中定义的符号。 这意味着如果共享库的静态符号表中存在与可执行文件同名的符号，链接器将使用程序中定义的符号而忽略共享库中的符号。 如果两个符号具有不同的实现或语义，这可能会导致未定义的行为。

如果需要使用共享库符号而不是程序符号，可以使用 -Bsymbolic 链接器选项强制链接器使用共享库中的符号。

当您使用 -shared 链接器选项创建共享库时，默认情况下，链接的目标文件中定义的所有符号都会添加到动态符号表中，除非它们被标记为隐藏或内部。

如果您不执行任何特殊操作来标记要导出的符号或隐藏它们，则共享库中定义的所有符号都将对链接到该库的任何代码可见。 这包括正在编译的源代码中定义的函数、变量和其他数据，以及从其他库导入的任何符号。

换句话说，即使您没有显式地标记任何导出函数，它们仍然可以被链接到共享库的其他代码链接和调用。 但是，最好只标记您打算成为库公共 API 的一部分以供外部代码使用的函数，并将任何内部函数或变量标记为隐藏或内部以避免不必要地公开它们。

请注意，当您将可执行文件链接到共享库时，只有可执行文件实际使用的符号才会包含在最终的可执行映像中。 这有助于减小可执行文件的大小并提高其性能。


动态符号表和静态符号表都是链接器在创建可执行文件或共享库时使用的数据结构，但它们的用途不同。

静态符号表，又称符号表，是编译器在编译源代码文件时生成的一种数据结构。 符号表包含有关文件中定义的所有符号的信息，例如函数、变量和其他数据。 表中的每个符号都有名称、类型、值（如果适用）和其他属性。 链接器在链接过程中使用静态符号表来解析不同目标文件之间的符号引用。

另一方面，动态符号表是链接器在将多个目标文件链接在一起以创建可执行文件或共享库时创建的数据结构。 动态符号表包含有关在生成的可执行文件或共享库中定义或引用的所有符号的信息。 动态符号表中的每个符号都有名称、地址、大小、可见性标志和其他属性。 动态符号表由动态链接器在运行时用来解析不同共享库之间或共享库与可执行文件之间的符号引用。

综上所述，静态符号表是链接器在链接过程中使用的，而动态符号表是动态链接器在运行时用来解析符号引用的。

在运行时使用 dlopen 加载共享库时，会发生相同的符号解析过程。 如果共享库的静态符号表中存在与可执行文件同名的符号，则符号解析过程将默认使用程序中定义的符号。 但是，可以在加载库时使用 RTLD_LOCAL 或 RTLD_GLOBAL 标志修改行为。 如果使用 RTLD_LOCAL 标志，符号将在本地解析，如果使用 RTLD_GLOBAL 标志，符号将在全局解析，类似于 -Bsymbolic 链接器选项。
对于生成动态库 默认都是添加的
对于可执行文件 如果使用了dlopen 建议在编译的时候 加入-rdynamic
它会把可执行文件的所有全局符号加如动态符号表  这样dlopen可以检查原本程序和外部库的符号碰撞问题

a.cpu引用了一个字  假设字在vp4

e.内核从磁盘讲vp4的内容复制到dram中,重新启动导致缺页的指令

9.7 抖动的原因

9.8 多级页表
32位的地址空间 每个地址指向1个字节  2^32个字节
4K的page   每个PTE都是4字节
那么一共需要 4MB的页表  (1MB个页表条目)

以上述内容作为条件
二级页表的典型例子

每个一级PTE指向1024个二级PTE  (相当于一个一级页表指向4MB的页)
但是注意这个相当于是全满的情况   如果二级PTE中只分配了一部分 那么只有这部分存在内存之中
而不是4MB都在

相当于索引的索引  
这样只需要1K个一级PTE  总共4K大小的一级页表就可以完整表述32位大小的内存空间

又因为只有一级页表和最常用的二级页表可以缓存在主存中 极大节省了内存

k级页表
把32位内存空间划分一下  3个10位  一个2位
10位的就是vpn 1 2 3
2位的就是vpo
比如那个vpn1 它指向一级页表1024个PTE中的一个(因为vpn1是10位,所以一级页表又2^10个PTE)
假设就是 第42个PTE
这个给第42PTE就指向第42个二级页表,然后vpn2就指向这个第42个二级页表中1024个PTE中的一个
假设就是 37

这个第42个二级页表里面的第37个PTE,指向第42个二级页表所指向的1024个PTE所指向的1024个三级页表的基址
然后VPN3指向这个三级页表的第xxx个
而因为只有3个vpn所以 vpn3指向的这个pte就宛如普通一级页表结构的内容一样了 一个有效位+PPN
PPN+PPO(VPO)=真实物理地址         (VPO=PPO) 具体见书p568 PTE结构
PTE(Page Table Entry)
页表条目
