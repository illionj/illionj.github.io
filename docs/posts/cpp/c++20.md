concept 

1.<=>

初始化建议用initializations
优势:什么类型都能用
可以用很多值初始化容器
检测窄类收缩和隐式类型转化
不会对函数声明或者函数调用感到困惑


现在你定义一个a==b(成员函数实现)  类型不一定相同,假设在a中存在对==成员函数

如果没有对应的函数,编译器会自己进行尝试 a != b // tries: a!=b, !(a==b), and !(b==a)
• A free-standing operator!=(TypeA, TypeB)
• A free-standing operator==(TypeA, TypeB)
• A free-standing operator==(TypeB, TypeA)
• A member function TypeA::operator!=(TypeB)
• A member function TypeA::operator==(TypeB)
• A member function TypeB::operator==(TypeA)
以上的函数任意定义一个 就可以支持a!=b
注意:同时存在独立函数的比较和成员函数的比较就会导致重定义错误
重写的表达式永远不会调用!=运算符(规定)
这也就是为什么一般都得默认实现==


一个良好的比较操作实现
声明 noexcept 如果不打算抛出异常
声明constexcept 如果打算在编译期使用
如果构造函数没有强制要求显式定义  声明操作符作为一个隐藏友元
声明 nodiscard 去警告未使用的返回值


注意三路比较运算符 不是int  也不能代替==  (因为==更快,并且直接返回bool)

三个问题  为什么<=>需要头文件   为什么<=>不能代替==  为什么<=>不设计成返回int
<=>优先于所有比较运算符
<=>仅限用于实现类型,永远都不用手写<=> 而是老老实实使用比较运算符

类内定义了 std::string  默认<=>就会被删除
默认比较顺序就是安装类成员顺序 进行比较  如果相等就继续  不相等就返回 类似strcmp

弱序的equal和equivalent   equal强调完全相等   equivalent突出强调排序准则下的相等
比如假设把一个容器存入set  我只以这个容器的第一个成员作为比较准则
那么对于那些第一个成员equal 其他成员不同的容器 它们是equivalent的

部分有序是针对集合中存在NaN这种不可排序的元素(比如浮点)  在这种集合中比较又可以产生所有的结果

strong_ordering -> weak_ordering -> partial_ ordering  可以从上至下转化

注意 operator!= 无法被<=>重写调用  它可以被==重写调用(这是规定,所以默认实现通常都是==)
但是全default除外,因为在这种情况下编译器会根据

如果比较链中的返回类型不同,应该手动声明最低的比较等级作为返回
如果你是在模板中进行使用,则可以使用common_comparison_category_t 它来判断比较链中的最低等级
如果是使用的默认<=>函数 则编译器会自动进行选择

strong_order可以简单实现浮点数比大小问题

对于空类 默认运算符对所有对象比较为相等

如果只定义了默认的<=>的函数  编译器会自动生成 完全一模一样(visibility, virtual, attributes,
requirements, etc)的 默认==运算符

注意 <=> 必须是常函数 也必须接受一个常引用

<=>在继承中的问题  
如果子类有一个default的<=> 
父类如果有<=> 则直接调用  父类没有<=> 但有== 和< 也可以
但是在第二种情况下 子类的default<=>不能使用auto了,因为编译器无法决定基类的排序顺序

std::compare_three_way 比<=>更强大  它甚至定义了对裸指针的强序比较


2.函数成员的占位类型

在14的时候就可以在lambda中使用auto作为函数占位符
在20中  auto可以在任意函数参数占位符使用(但是在这种情况下似乎不支持分离编译)
一旦使用了auto 等效于函数模板,这种方式也可以被成为简化函数模板语法

经过测试 模板可以利用特化进行分离编译  但这个auto似乎不行
类内的auto也是一样的  使用auto就必须放在类内了

auto的重要用途
1.解决循环依赖
原本解法 
1.前向声明一个类c2  
2.定义一个类c1,在c1使用c2指针或者引用的函数中只给出声明 
3.完整给出c2的实现(c2中存在使用c1的函数)
4.给出c1中使用c2的那个函数的inline定义

现在解法1
不需要前向声明,直接auto

现在解法2(推荐) 
前向声明  直接auto 使用concept std::same_as进行约束

auto的普通函数和使用auto的lambda是不同的
auto的普通函数就是简写的模板 它无法在不指定类型的情况下被间接使用 比如传递给sort进行排序
使用auto的lambda它本身不是一个泛型,它是一个重载了()的class .只有把lambda作为函数使用的时候才是泛型(相当于直接调用).它可以被直接传递给sort

auto细节
无法使用decltype(auto)

再次强调 auto函数完全等价于函数模板 以下实例原则上等价

template<typename T>
void foo(auto x, T y, auto z);

template<typename T, typename T2, typename T3>
void foo(T2 x, T y, T3 z);

注意 混合模板与auto参数的时候要小心,应该与声明顺序一致  模板优先

2.ranges and views

ranges
views
pipeline

相比于普通algrithm里面的算法,比如 sort和ranges::sort和ranges
ranges中的算法会多一些特点

1.它们使用cocept约束itreator和ranges
2.返回值可能会有一些变化
3.可能返回borrowed iterators 因为传递进来的ranges很可能是临时量
4.std::dangling  空类型兼占位类  如果传入的变量属于临时变量并且没有对应borrowed iterators的实现


remove 和remove_if 不改变容器 它只会把要删除的元素放在最后 
所以还需要用erase(it,coll.end())

ranges的命名空间中存在大量和原本std中类似功能相同名字的api,按照一个基本的原则,如果两者都可以使用则应该优先使用ranges中的


std::ranges::range 是所有其他ranges概念的基础,它们都包含std::ranges::range

views的一种轻量级的ranges 可以非常便宜的创建  复制 和移动
views的功能: 
ranges和子ranges的引用 
拥有临时ranges
过滤元素
生成元素的转变值
自己生成一系列值

std::map是有序的  红黑树
所以在用views遍历的时候有序
unordered_map是hash  它就是无序的


views 自己的filter transform take 
中间都不会保存任何内存
在定义的时候也不会进行计算
定义一组views的时候它们只是用规则进行一种叠加
当真的在对应ranges或者views(ranges)上进行遍历的时候,才会挨个进行计算
比如一个vector 按照 filter transform take  的顺序进行操作
他会先取第一个元素  然后filter  然后transform  然后计算take  如果满足take之后就会结束
如果没有满足take就继续取下一个元素

比如给  `auto t1 = views::transform( [](auto elem){ return elem * elem; });`
		`auto t2 = views::transform(coll, [](auto elem){ return elem * elem; });`

t1就是一个规则  t2则是一个规则外加一个目标    t2 == coll|t1  (功能一致)

views本质就是函数式里面pure函数,它自己不会储存改变任何的变量,它只是一个规则

这个非常像haskell里面概念啊

views 应该只使用小型或者平凡的内联函数
views是可读写的
