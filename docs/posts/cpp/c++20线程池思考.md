# C++20 线程池思考

<!-- more -->

原始版就不看了,有点丢人显眼 
直接看改进版

struct Task{
	std::packaged_task<void()>pt;
}
先来看std::packaged_task<void()>pt;
std::packaged_task的核心职责就是将一个可调用对象和一个promise绑在一起

这就是回到了promise和future
在线程和任务之间,安全的传递结果(包括返回值或异常)的同步原语
std::promise是生产者接口
std::future是消费者接口
简单用法就是
创建一个promise对象,然后从它身上获取future
然后在线程中传入promise对象,完成生产之后调用set_value或者set_exception存储值
外面就是调用future.get 来获取这个值,也不用担心同步问题,get会自动等待promiseset成功
所以能看懂promise为啥叫promise  ,一定会set.如果不set会抛异常
future 是一次性使用,且move-only 只能get一次
(当然还有一种shared_future,可以多次使用)


std::mutex m_;
确实该好好说是这个std::mutex了
它本身只提供加锁和解锁
但是我们有各种各样的需求



lock_guard／scoped_lock／unique_lock

std::mutex 最基本的非递归互斥量,不可拷贝,不可移动
只有上锁解锁两个功能
同一线程调用两次lock就会死锁
效率最高


std::timed_mutex  可以使用接口检查一定时间中能不能获得锁,相对于带个超时检查
std::recursive_mutex 允许同一线程多次lock  (但需要多次unlokc)
std::shared_mutex 读写锁
std::shared_mutex sm;
// 读者
sm.lock_shared();
// … 只读临界区 …
sm.unlock_shared();
// 写者
sm.lock();
// … 写临界区 …
sm.unlock();

RAll锁封装类型 
std::lock_gurad 
最简单的锁,构造即锁,析构解锁  不可手动解锁,不可移动


std::unique_lock  构造可锁,也可延迟锁  能手动解锁,也能移动
功能最全的锁封装
延迟锁定,尝试锁定,超时锁定,手动解锁再锁定,移动语义


std::scoped_lock 构造即锁,管理多个互斥锁
一次性安全锁定多个互斥量
内部使用std::lock(m1,m2,m3) 内部使用防死锁算法,一旦尝试获取锁失败就会释放之前已经获取的锁


std::shared_lock<SharedMutex> 针对读写锁封装

还有锁标签
std::defer_lock 构造不枷锁,后续手动lock
std::try_to_lock 构造尝试锁定异常,失败不阻塞
std::adopt_lock  构造时假设当前线程已经持有互斥量,不再lock,析构时释放
std::try_lock_for...  前文介绍的超时版本


condition_variable
互斥量解决的时候临界区并发访问的问题,保证一个时刻只有一个线程共享数据
条件变量则是当共享数据满足某个条件的时候才能继续,让条件不满足的时候股权并释放锁
condition_variable强依赖unique_lock
condition_ variable的predicate必须要有,因为存在虚假唤醒的可能
至于虚假唤醒,这是平衡性能和标准的举措,虚假唤醒不是bug,而是特性
使用的condition_variable的时候最好能提前释放锁,能早释放就早释放

atomic 原子量 
c++20新增了一个std::atomic_ref<T>


  void worker() {
    while (true) {
      Task task;
      {
        std::unique_lock lk(m_);
        cv_.wait(lk, [this] { return stopping_ || !q_.empty(); });
        if (stopping_ && q_.empty()) break;
        task = std::move(q_.front());
        q_.pop();
      }
      try {
        task.pt();
      } catch (...) {
      }
    }
  }

非常典型的一个工作函数,它会被放在线程中无限循环,直到接受到信号并且工作全部完成后
先是取锁 std::unique_lock 
然后使用std::condition_variable 进行条件检查 如果任务队列不空,或者存在终止信号,立刻执行
然后检查是否同时存在终止信号和任务队列为空,真则结束退出循环,结束线程
从q.front的移动出,然后探出q
{看明白为啥要括号了吗,尽早释放锁}

重头戏来了,添加函数,显而易见这里希望可以添加任意类型
当然退一步也是可以的,submit接受function<void()> 然后外部传入的都包装好的lambda



从模板上就能只知道 这是一个变参模板
然后尾置声明  std::future<std::invoke_result_t<F, Args...>>
一层层看  std::invoke_result_t<F,Args...> 这是对传入函数进行一次类型萃取
它就是F的返回值类型
然后std::future的模板参数也是这个类型
合起来就是 submit提交一个函数到线程池的时候会返回一个future,函数执行完毕后可以从future获取执行结果

接下来看到4个pt,三个注释一个实际执行
先来看看packaged_task是什么,为什么已经有了std::promise和std::future 依然需要std::packaged_task
promise和future是更灵活的,它只表示有个值存在,未来由future获取
而std::packaged_task突出强调这个值就是一个可调用对象的返回值,未来由future获取,相当于std::packaged_task封装了一个最常用的场景供其他人使用


auto pt=std::packaged_task<R()>(std::bind(std::forward<F>(f),std::forward<Args>(args)...));
先看第一个pt
它是怎么做的呢,利用折叠表达式展开,将参数包和函数打包成一个R()类型的可调用对象
但是bind不太好,各方面都很垃圾,所有推荐换成lambda

auto pt=std::packaged_task<R()>([=]{return f(args...);});
姐妹写法   auto pt=std::packaged_task<R()>([&]{return f(args...);});

先说第一种,只能拷贝,不能移动;丢失完美转发;不能处理不可拷贝的内容
第二种就更完蛋了,引用在函数结束的时候全部销毁
&捕获的时候对args和f的引用,lambda结束的时候args和f会销毁

auto pt = std::packaged_task<R()>([func = std::forward<F>(f),                    // 捕获并完美转发 f
                                    ... capturedArgs = std::forward<Args>(args)]  // ← 关键：把 ... 放到名字前面
                                   () mutable {
                                     // 再次完美转发实参；也可以 std::move
                                   return std::invoke(std::move(func), std::move(capturedArgs)...);
标准的c++20写法,包捕获
先是两个完美转发获得函数和入参
然后开启mutable,使其可以在函数内部调用std::move,返回一个 绑定好的 std::invoke

c++20中存在各种各样包装函数方式
比如lambda function bind
为啥还又一个std::invoke 与其配套的std::invoke_result_t等
首先要明确一个概念 invoke不是包装,而是直接调用
它存在的意义是对各种各样的可调用对象,提供一个统一的调用方式
比如函数指针可能需要
(*p)()
引用或者lambda 需要p()
std::invoke的作用就是不管p是什么东西,把它填到invoke的首个参数就能调用了

再回头看这个lambda,它的作用就是提供一个统一的bind ,让外部变成R(),完美转发可以让外部的std::ref生效
内部使用std::invoke处理各种各样的可调用对象

std::apply感觉和std::invoke很像,对于c++20之前,它们解决的场景不同
对于std::apply 它接受一个可调用对象,和一个Tuple
如果入参是参数包的形式,那么常规做法就是参数包先打包成tuple,然后tuple传给apply
apply内部进行拆包,然后调用invoke执行
所以可以简单的把上述方式看作一个经典做法

再来看这个pt,它的特点在于没用c++20的包捕获(c++20之前,包展开不能写在lambda中),而是使用传统的apply

    auto fut = pt.get_future();

这里就是从pt中获取future,如果需要处理fut的返回值,推荐用std::any聚合存储.
不需要可以都写成void的形式,方便容器存储
后面一个局部块,使用lock_guard获取任务队列的锁,.如果原子量stopping_已经为真,就抛异常
      q_.push(Task{std::packaged_task<void()>([p = std::move(pt)]() mutable { p(); })});
